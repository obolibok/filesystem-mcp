## Замечания к приёмке

### R1 — P1: неограниченный cache путей в ignore matcher

Место: `src/core/snapshot-pipeline.ts:101`, вызов `rule.matcher.test(candidate)`.
Библиотека `ignore` сохраняет каждый проверенный путь во внутреннем `_testCache`.
Корневой matcher с `.gitignore` живёт весь обход: streaming CSV не устраняет
линейный рост памяти по числу файлов. Это важно для целевых миллионов записей.

Synthetic воспроизведение с одним matcher `ignored/` + `*.tmp` и уникальными
путями: 100 000 файлов оставили 100 200 cache entries / heap около 31,2 MB;
300 000 — 300 600 entries / около 70,3 MB. Большой metadata benchmark вызывает
producer записей напрямую и не проходит этот участок; real-walk на 21 000
файлов недостаточен для вывода о bounded memory на миллионах файлов.

Исправить стратегию matching так, чтобы cache и накопленные правила имели
обоснованную верхнюю границу. Сохранить nested ignore/negation semantics.
Добавить масштабный regression самого обхода с `.gitignore`, сравнить рост
памяти при одинаковых caps и разном количестве путей. Не писать тест, который
подменяет walk генератором metadata и поэтому обходит источник роста.

### R2 — P1: ошибка ZIP producer завершает процесс сервера

Место: `src/core/snapshot-pipeline.ts:301–309`. Код ожидает `zip.outputStream`,
но не обрабатывает отдельное событие `error` объекта `yazl.ZipFile`.
Удаление закрытого CSV spool перед упаковкой приводит к `ENOENT` в `yazl`,
`Unhandled 'error' event` и exit code 1 дочернего процесса вместо job `failed`.
Одна ошибка чтения scratch завершает endpoint и прерывает остальные jobs.

Связать ошибки producer с ожидаемой операцией и управляемым завершением job;
при ошибке/отмене останавливать producer и streams, закрывать handles и
освобождать временные файлы. Добавить fault injection реального ZIP producer
(ошибка stat/open/read spool), проверить, что сервер жив, job terminal failed,
нет доступных partial artifacts и последующее задание выполняется.

### R3 — P2: параллельный expiry дважды освобождает квоту

Место: `src/core/job-manager.ts:615–618` и `601–607`. Два вызова проходят
проверку `resultExpired` до первого `await #removeArtifacts`; оба затем
вычитают размер того же файла из `#usedBytes`. Вызовы cleanup/status могут
пересекаться в обычном работающем endpoint.

Воспроизведение непосредственно на TypeScript manager: два persisted completed
jobs с артефактами по 256 KiB, для одного истёк TTL;
`Promise.all([cleanupExpired(), cleanupExpired()])`. После очистки на диске
264 285 bytes, но резервирование ещё 921 600 bytes проходит при квоте
1 048 576 bytes. Фактическая сумма составила бы 1 185 885 bytes. Последовательная
очистка отклоняет ту же reservation корректно.

Сериализовать/idempotently выполнять удаление по job и однократно освобождать
учёт. Сохранять защиту active reads. Добавить regression параллельных expiry
вызовов с проверкой квоты по реально оставшимся файлам, а не только job state.

### R4 — P2: restart не учитывает окончательный файл без metadata

Место: `src/core/job-manager.ts:528–538` и `269–275`. Artifact сначала
переименовывается из `.partial` в окончательный UUID-файл, затем metadata
сохраняет его descriptor. Падение между этими операциями оставляет final ZIP,
который отсутствует в `job.artifacts`. Recovery удаляет только `.partial` и
`.metadata-tmp`; orphan сохраняется без учёта в scratch quota.

Synthetic persisted state воспроизводит это окно: running job и неописанный
256 KiB final ZIP. После restart job `interrupted`, ZIP остаётся на диске;
при фактически занятых 263 191 bytes manager разрешает дополнительные
921 600 bytes при квоте 1 048 576 bytes.

При recovery сверять собственные файлы job directory с metadata. Безопасно
удалять незавершённые результаты, сохраняя quota charge до реального удаления;
не удалять произвольные чужие файлы. Проверить crash после rename до persist,
ошибку удаления и повторный restart. Автоматический resume обхода не нужен.

### R5 — P2: жёсткий walk-depth cap превращается в completed

Место: `src/core/snapshot-pipeline.ts:237–239`. Общий catch рекурсивного обхода
перехватывает `TOO_LARGE` от ограничения глубины, считает его ошибкой доступа
и прекращает перечисление оставшихся соседей в родительском каталоге.

Воспроизведение: `maxWalkDepth=8`, каталог глубины 9 и допустимый соседний файл
на глубине 8. Получены `completed`, `complete=false`, `filesWritten=0`, ZIP и
manifest. Жёсткий лимит должен завершать job понятной ошибкой; существующий
контракт не разрешает публиковать результат hard-cap failure как completed.

Разделить ожидаемые ошибки доступа/исчезновения и ошибки policy/quota/internal.
Добавить regression, проверяющий terminal state, stop reason и недоступность
артефактов при hard-cap failure. Сохранить допустимый partial-completeness
контракт для отдельных недоступных/исчезнувших файлов.

### R6 — P2: ZIP verifier допускает повреждённые/лишние entries

Место: `scripts/snapshot-benchmark/run.mts:115–119`; аналогичная ранняя фиксация
успеха в `__tests__/snapshot.test.ts:77–79`. Benchmark resolve-ит Promise после
первого CSV, не запрашивая следующие entries. В тестовом helper следующий entry
запрашивается, но Promise уже resolve-ится до его обработки. CRC не вычисляется;
`validateEntrySizes` в `yauzl` не подтверждает CRC.

Воспроизведение на извлечённой без изменения функции benchmark verifier:
ZIP с двумя entries принят как корректный однострочный snapshot; обнуление CRC
в central directory также не привело к отказу. Следовательно, утверждение
`11 CRC-valid ZIP/CSV частей` в benchmark report пока не подтверждено.
SHA-256 из manifest не заменяет integrity check: producer может хешировать
некорректно сформированный архив.

Проверять ровно один ожидаемый CSV entry и успешное завершение всего ZIP,
вычислять/сравнивать CRC распакованных bytes, корректно обрабатывать ошибки
stream/parser. Добавить отрицательные fixtures: extra entry, bad CRC, усечение,
повреждение сжатых bytes. Повторить benchmark с исправленным verifier и
уточнить отчёт; обычный CSV также должен проходить независимый parser.

### R7 — P2: completed snapshot содержит недоступную для выдачи часть

Место: `src/core/snapshot-pipeline.ts:312–315`; выдача ограничивается отдельно
в `src/core/job-manager.ts:465`. Producer проверяет только `maxZipBytes`, а
get_artifact применяет минимум `maxDeliveryBytes` и действующего общего file cap.
Эти настройки могут различаться, но несовместимость не учитывается при создании.

Воспроизведение на реальном producer/manager с допустимыми настройками:
`maxDeliveryBytes=65536`, `maxZipBytes=1048576`, 3000 synthetic records.
Получены CSV 955 947 bytes, ZIP 243 296 bytes, `completed`, `complete=true`.
Manifest 1797 bytes доступен, а получение ZIP отклоняется с `TOO_LARGE`:
243 296 > 65 536. Завершённая job не выполняет цель доставки результата.

Ограничивать producer эффективным минимумом ZIP/delivery/общего file cap либо
заранее отклонять несовместимую конфигурацию с понятной ошибкой. При превышении
допустим bounded failure; completed с неполучаемыми частями недопустим.
Добавить regression для обоих более строгих лимитов и проверить manifest.
Повторная проверка текущего лимита на fetch после изменения конфигурации нужна;
это не отменяет согласование caps при создании job.

## Уточнить доказательства acceptance

Сейчас в карточке отмечены некоторые более широкие гарантии, чем проверяют тесты:

- Cancel проверяется на producer, который сам не завершится; это не воспроизводит
  гонку нормального completion и cancel. Нужны обе последовательности около commit.
- HTTP test закрывает клиента после успешного submit response. Потеря ответа /
  короткий client timeout после принятия job и восстановление через idempotency
  key должны проверяться отдельно, без отмены самой job.
- Quoting/multiline test сверяет bytes с тем же production serializer; добавить
  независимый CSV parse/round-trip с принудительной границей частей.
- Access narrowing проверяет status; проверить также cancel/fetch и после restart.
- Poor-compression runner печатает `verifiedBoundedFailure` без assertion,
  что не осталось готовых/partial artifacts. Зафиксировать это утверждением теста.

Это продолжение существующих критериев 003, не расширение scope. Исполнитель
должен сопоставить каждый отмеченный пункт с фактическим сценарием и снять
неподтверждённые галочки до появления доказательства.
