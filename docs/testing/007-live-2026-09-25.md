## Два отказа metadata rename

По пользовательскому отчёту:

| Job                                  | Live state | filesWritten | Fatal          |
| ------------------------------------ | ---------- | -----------: | -------------- |
| d5f69bf1-e988-45d7-8388-f04ead34affa | failed     |        50000 | EPERM / rename |
| 13825c34-d835-4911-9ce0-a825537edd57 | failed     |       160000 | EPERM / rename |

Операция — `job.<uuid>.metadata-tmp -> job.json` в scratch, не source path.
FatalError в live включал code/path/nativeErrorCode/operation.
Независимое чтение persisted job.json выявило дополнительную потерю:
первый остался running / 40000 файлов, второй running / 150000 файлов;
у обоих нет finishedAt и fatalError. На диске последняя успешная checkpoint,
а не наблюдавшийся клиентом terminal result. После restart текущая реализация
превратит такой running в interrupted и не восстановит несохранённую fatal причину.

## Что подтверждено кодом и synthetic reproduction

В проверенном runtime:

- `getJob` после initialize получает job из in-memory map, выполняет authorization
  и expiry. Для running job он не читает job.json. `job_status` вызывает getJob.
  Поэтому гипотеза отчёта о read-handle самого polling пока не подтверждена.
- Запись сериализована по job. `replaceMetadataFile` уже повторяет
  EPERM/EACCES/EBUSY: 8 попыток, задержки 10+20+30+40+50+60+70 = 280 ms,
  не считая времени файловых операций. Этот код есть в принятом 006 baseline.
- Ошибка checkpoint переводит job в failed в памяти. Финальная запись использует
  тот же короткий retry. При её отказе worker только пишет лог; последующей
  попытки после снятия блокировки нет, close не сохраняет уже failed job снова.

Независимый synthetic reproducer на Windows/Node 24.15.0, только isolated scratch.
Отдельный PowerShell открывает job.json через FileShare.ReadWrite без Delete,
удерживает handle указанное время и гарантированно закрывает его. Production
файлы не блокировались. Для control использован producer с 500 checkpoints;
getJob вызывался в фоне с интервалом 1 ms.

| Сценарий                                                  | Получено                                                                                          |
| --------------------------------------------------------- | ------------------------------------------------------------------------------------------------- |
| 500 checkpoints, 730 status reads, без внешней блокировки | completed в памяти и на диске                                                                     |
| Handle удерживается 50 ms                                 | completed в памяти и на диске                                                                     |
| Handle удерживается 1500 ms                               | failed EPERM/rename в памяти; running без fatalError на диске, в том числе после закрытия manager |

Reproducer не доказывает, кто удерживал файл в пользовательском опыте.
Причины вроде антивируса/индексатора остаются гипотезами; уменьшение polling
не принимается как исправление. Контрольный прогон также не доказывает отсутствие
любой возможной гонки при иной нагрузке.

## Следующие действия

Подготовлена [008: надёжность metadata persistence](../tasks/008-job-metadata-persistence.md).
Нужны bounded recovery при более долгой transient блокировке, работа с terminal
persist failure и независимые tests для polling/Windows handles/restart/close.
Отдельная малая правка: non-fatal ACCESS_DENIED сейчас получает общий текст
`Job failed`; сообщение должно описывать отказ доступа, не итог всего job.
Новый coding-чат ещё не назначен. Исходные источники и собранный inventory
не нужны исполнителю; требования и воспроизведение сохранены в этой карточке.
