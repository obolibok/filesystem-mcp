## R8 — P2: временная ошибка TTL-очистки блокирует запуск endpoint

Место на проверенном head: `src/core/job-manager.ts:696–699` — новый throw
ошибки удаления; startup ожидает expiry без обработки ошибки в строке 243.
`initialize()` сохраняет этот rejected Promise в строках 207–209.
`createServer` и stdio factory ожидают initialize до готовности endpoint.

Воспроизведение на исходниках через добавленный `unlinkFile` seam:

1. Создать persisted completed job с истёкшим TTL и ZIP размером 65 536 bytes.
2. Один раз вернуть `EACCES` при unlink этого артефакта; последующие удаления
   разрешить. Это моделирует временную Windows-блокировку файла.
3. Первый `initialize()` отклоняется с `EACCES`, ZIP сохраняется.
4. Второй `initialize()` и `close()` отклоняются той же ошибкой; счётчик unlink
   остаётся 1, новой попытки нет, даже когда удаление уже возможно.

Причина — recoverable ошибка обслуживания scratch превращается в постоянный
failure manager initialization. Недоступен весь MCP endpoint, включая обычные
файловые инструменты. Исправление учёта неудалённых bytes правильно; его сохранить.

При startup failure удаления оставить артефакт charged и недоступным после TTL,
записать диагностическое сообщение и позволить серверу запуститься. Последующая
cleanup должна повторить удаление и освободить квоту ровно один раз. Не сбрасывать
инициализацию вслепую: повторная загрузка metadata не должна удвоить учёт.

Regression должен проверить одноразовые EACCES/EPERM, успешный initialize,
недоступность expired bytes, сохранение quota charge, успешное новое задание,
повторный cleanup после снятия блокировки и корректный close. Фатальные ошибки
самого scratch/root по-прежнему должны диагностироваться честно.
