## R4 — P2: резерв частично записанного ZIP освобождается до удаления

Место: `src/core/bundle-pipeline.ts:464-474`, cleanup `:505-507`.

Классификация ошибок capture storage исправлена: они завершают job как failed,
а не превращаются в per-file inaccessible. Однако при записи ZIP catch всё ещё
вызывает `releaseDisk(chunk.length)` до удаления файла. Внутри цикла уже мог
успешно завершиться короткий write части этого chunk; `zipBytes` увеличивается
только после успешной записи всего chunk. Если удаление тоже недоступно, оставшиеся
bytes исчезают из учёта общей scratch quota.

Независимое воспроизведение на synthetic original 1 MiB:

1. Использовать обычный bundle pipeline и общий ArtifactJobManager.
2. После начала compression перехватить только ZIP write: первая запись большого
   chunk реально сохраняет 8192 B и возвращает успешный `bytesWritten=8192`;
   следующая запись оставшейся части возвращает EACCES.
3. Через manager unlink hook вернуть EACCES только для этого `.zip.partial`,
   включая повторный cleanup. Остальные операции удаления работают.
4. Дождаться failed job и `manager.close()`, сравнить stat partial с temp accounting.

Результат: `failed`, artifacts отсутствуют; на диске `.zip.partial` **8235 B**, но
`runtime.tempBytes` **43 B**. Неучтённые 8192 B остаются на диске. Последующие jobs
могут резервировать место без учёта этих bytes, нарушая общий storage limit.
Это проверка последовательных successful-short-write / rejected-write, а не
предположение о неизвестных bytes внутри одной отклонённой операции.

Исправление: хранить резерв записи до успешного удаления; при сохранении partial
учитывать как минимум реально оставшиеся bytes. Не освобождать полный chunk только
потому, что следующая запись завершилась ошибкой. Regression должен одновременно
покрыть partial write и неудачное удаление, проверить квоту для следующей job,
а затем освобождение резерва после успешной очистки. Не менять fatal storage policy.

## R3 — P2: внутренние compression streams остаются до GC

Место: `src/core/bundle-pipeline.ts:482-487`; создание цепочки через
`zip.addReadStream` находится в `:442-455`.

Исходный source FileHandle теперь закрывается. Но cleanup уничтожает и ожидает
только source streams и конечный output. Между ними yazl создаёт CRC/counter/
DeflateRaw/counter pipeline через `.pipe()`, который автоматически не уничтожается
при закрытии этих двух концов. Превышение ZIP cap используется и для штатного split.

Независимое воспроизведение:

1. Synthetic poorly-compressible original 8 MiB, ZIP/delivery cap 64 KiB.
2. В одном manager последовательно выполнить восемь jobs; каждая завершается
   completed с included=0, tooLarge=1 и без ZIP part.
3. Наблюдать pipe destinations только через WeakRef/WeakSet; через `async_hooks`
   считать init/destroy ресурсов ZLIB, не сохраняя сильных ссылок на stream.
4. После `manager.close()` и ещё 300 ms проверить ресурсы; отдельно выполнить GC.

Результат: перед принудительным GC **created=8, destroyed=0, live=8**; у DeflateRaw
`closed=false`, native handle сохраняется. После GC все восемь освобождаются.
Это подтверждает незавершённый cleanup и накопление native ресурсов до GC,
**не доказывает постоянную утечку**. Старое замечание об открытом source FD закрыто.

Исправление: обеспечить владение и завершение всей compression pipeline на
oversized/split, cancel и error, включая внутренний compressor; ожидание завершения
не должно зависеть от GC. Regression должен наблюдать compression resources,
а не только переданные `onZipSource` источники. Последующая job должна работать
на том же manager, ZIP bytes и текущие лимиты должны сохраниться.
