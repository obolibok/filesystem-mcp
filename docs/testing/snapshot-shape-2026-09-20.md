## Проверки содержимого и их границы

CSV разобраны потоково Python csv.reader с strict parsing непосредственно из ZIP.
Прочитаны все записи и проверены CRC всех entries. Декодированное/повторно
закодированное число bytes плюс BOM совпало с ZIP metadata каждой части.

- Во всех строках пять полей; ошибок UTF-8, повторных headers в данных,
  multiline-записей и некорректного неотрицательного целого Length не найдено.
- FullName, Name, Length, LastWriteTime заполнены; пустой Extension у 28 722 записей
  допустим для файлов без расширения. FullName абсолютный во всех строках;
  его basename совпадает с Name.
- LastWriteTime записан текстом с датой через slash. Новая схема должна явно
  определить timezone и машинный формат времени, а не зависеть от locale.
- Отсутствие multiline в этом наборе не разрешает резать произвольный CSV по
  физическим строкам: новый writer/reader должен сохранять целые CSV-записи.

CRC и корректный CSV не доказывают полноту исходного обхода, отсутствие дубликатов
или соответствие нынешнему диску. В архиве нет отдельного manifest с политикой
обхода, ошибками доступа, исключениями, интервалом наблюдения и признаками усечения.

## Измерение самостоятельных ZIP

Каждая существующая CSV-часть повторно сжата отдельно через стандартный Python
zipfile, DEFLATE level 6, потоками по 1 MiB. Выход — счётчик записанных bytes,
без сохранения новых ZIP. Это измерение сериализации/сжатия, не тест передачи в ChatGPT.

- Обычный самостоятельный ZIP с одной CSV-частью: 1 465 809–5 527 543 bytes.
- Base64 одной такой ZIP-части: 1 954 412–7 370 060 символов, плюс MCP JSON/metadata.
- Base64 исходного общего ZIP: 46 882 044 символа, плюс MCP JSON/metadata.
- Все отдельные ZIP меньше текущего default get_file raw cap 10 MiB; общий ZIP
  превышает его. Это серверный лимит, не подтверждённый предел принимающей среды.
- Повторное сжатие всех частей: 6,661 секунды; peak working set этого Python
  процесса 21 889 024 bytes. Полный предыдущий CSV-разбор: 34,968 секунды.
  Это одиночные локальные измерения, не benchmark будущего Node-коннектора
  и не оценка скорости обхода исходного дерева/сети.

## Следствия для 003/004

1. В 003 нужны фоновые задания со статусом/отменой, потоковое формирование CSV,
   разбиение на полные записи, сжатие, bounded scratch и получение частей.
   Повтор запроса получения не повторяет 20–30-минутный обход.
2. Готовый результат — небольшой versioned manifest и самостоятельные ZIP-части.
   Фактическое сжатие зависит от данных; размеры CSV и ZIP ограничиваются отдельно,
   включая header/BOM, ZIP overhead и base64. Старые примерно 45 MiB — отправная
   точка для эксперимента, не универсальная настройка или клиентский предел.
3. Для следующего live опыта нужен synthetic архив порядка максимальной измеренной
   части (около 5,53 MB) с независимой проверкой файла на принимающей стороне.
   Рабочую границу закрепить только после size ladder; production архив туда
   автоматически не отправлять.
4. Схема прежнего CSV полезна как совместимая проекция. Для нового snapshot
   рассмотреть root ID + relative path, явную схему времени и metadata полноты.
   Не менять семантику FullName молча. Хеши частей обязательны; массовое чтение
   и хеширование содержимого оригиналов не нужны для metadata snapshot.
5. Нагрузочный профиль pipeline — примерно 3 млн записей / 450–500 MB до сжатия,
   плюс плохо сжимаемые synthetic данные. Нагрузку обхода реальной synthetic ФС
   и поведение при длительной работе проверять отдельно.
6. 004 добавляет сборку выбранных originals поверх той же основы заданий,
   хранения, упаковки и доставки. Дублировать этот механизм не требуется.

Общее [проектное предложение](../project/snapshot-bundle-design.md) остаётся
предложением; карточка реализации и конкретные параметры ещё не утверждены.
