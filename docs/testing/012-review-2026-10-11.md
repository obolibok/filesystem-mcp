## R1 P2 Неверный default search_text и отсутствующий стандартный workload

Место: `docs/testing/012-pagination-memory.md:128`, матрица `run.mjs:254–281`
(default-pages), `common.mjs:137–157` (явный page-size query).

В отчёте pageSize=100 назван baseline default search. Но весь search workload
использует search_text, у которого опубликованный default maxResults равен
**500**; в 011 новый default pageSize также 500. Значение 100 принадлежит
find_files. Default-pages дополняет только list, не search_text.

Независимый real MCP опыт на точной long fixture harness (128 совпавших строк,
context=10) и исходном runtime:

| Запрос                                  | Всего matches | nextCursor/resource | Page sets / resources |
| --------------------------------------- | ------------- | ------------------- | --------------------- |
| Без maxResults, фактический default 500 | 128           | Нет / нет           | 0 / 0                 |
| Явный maxResults=100                    | 128           | Есть / есть         | 1 / 1                 |

Поэтому 88 MiB удержания страниц для 32 таких запросов характеризует именно
принудительно уменьшенную страницу, а не обычный default вызов на этом файле.
Само измерение p1/p100 полезно и не опровергается: нужно явно ограничить его смысл.
Фраза о независимости retention от размера страницы требует условия: набор
должен оставаться paginated; при вмещении на одной странице store не создаётся.

Исправить default и выводы, добавить реальный handler case с пропущенным page
параметром и опубликованным default. Проверить обе стороны границы: набор на
одной странице и synthetic набор >500 matches, безопасный для per-file/resource
budget. Harness должен поддерживать ожидаемое отсутствие cursor/resource, а не
обязательно считать его failure. Включить соответствующий повтор после 011.
Сохранить исходные p1/p100 результаты с точными условиями применимости.

## R2 P2 Harness теряет признаки неполноты измеряемого поиска

Место: `scripts/pagination-check/worker.mjs:117–129`, `151–162` и
`scripts/pagination-check/run.mjs:72–86`, fresh/HTTP query handling.

Fresh проверяет isError/наличие cursor (и resource в HTTP), сохраняет collected
count, но не записывает truncated/stoppedReason/skipped counters и не сверяет
результат с ожидаемым fixture/limit. В HTTP число строк сохраняется только от
первого запроса. Если timeout или иной stop возвращает успешный partial result,
он может попасть в ту же сравнительную таблицу как обычный completed workload.
В отчёте предлагается сверять count/truncation после 011, но truncation отсутствует
в output JSON; утверждение «ожидаемые totals без truncation» harness не закрепляет.

Независимый контроль через неизменённый worker:
kind=handler, tool=search_text, matches=10001, width=32, context=0, pageSize=1,
sets=1, isolation=both. Получено 10000 вместо 10001 из-за действующего scan cap;
worker завершился успешно, emitted result и passed cursor replay. В checkpoint
нет ни truncated, ни stoppedReason. Это намеренный partial input, не дефект
поискового сервера: он показывает, что стенд не различает категории результата.

Сохранять effective contract, collected count, stop/truncation и существенные
skip counters для fresh queries и сопоставлять с рассчитанным expected outcome.
Обычная полная fixture должна отвергать неожиданный timeout/cap/skips; намеренно
частичная нагрузка может пройти, но с явно записанной причиной и отдельной
категорией, исключающей нечестное сравнение с complete. Проверить handler и HTTP,
в том числе простой negative control с partial/timeout ответом. Budget stop
процесса/числа sets оставить отдельным от search scan truncation.
