# 014: независимый live-прогон трёх корней — 29.10.2026

Прогон выполнен на новом комплекте с отдельным scratch, последовательно по трём разрешённым корням. Для каждого запускались `snapshot(forceRefresh=true)` и затем `snapshot_tree(forceRefresh=true)` с `includeHidden=false` и `includeIgnored=false`; каждому job передан новый idempotency key. Корни обозначены R1–R3 в порядке `list_roots`; реальные пути, имена файлов, host/volume IDs и документы не сохраняются.

## Доставка и локальная обработка

- SHA-256 manifest проверен для всех пяти созданных manifests.
- R1 и R3: все manifest/ZIP parts получены; размер, SHA-256 и ZIP CRC совпали. Получено около 3.04 MB R1 artifacts и 14.64 MB R3 artifacts.
- R2 stable: manifest содержит 11 частей. Части 1 и 3–11 получены и прошли проверки размера, SHA-256 и ZIP CRC. Пользователь подтвердил, что часть 2 видна в каталоге jobs и открывается в Excel; Windows Explorer показывает 5,318 KB, что совпадает с ожидаемыми 5,445,076 B. Мои вызовы `get_artifact` по ней возвращали `NOT_FOUND`, поэтому локальный harness получил 10 частей и обработал 2,466,397 файлов. Это несоответствие в assistant-side выдаче, а не подтверждённая потеря server artifact.
- R2 tree не сформировал deliverable части: `stopReason` — `Closed ZIP part would exceed effective deliverable cap 8388608 bytes`; `fatalError=TOO_LARGE`. Первая часть накопила 47,185,893 B CSV и не была выдана.
- Локальный Node harness распаковал и проверил CRC R1 stable/tree за 0.95/0.28 s; разбор двух CSV занял около 0.69 s. Для R2 stable 10 доступных частей обработаны за 28.34 s; это не покрывает отсутствующую часть. Для R3 stable/tree локальная распаковка, проверка и разбор заняли 7.66/4.21 s.

## Сверка путей и поиск

- R1 и R3: число файлов совпало; ordered SHA-256 по восстановленному относительному пути, длине и LastWriteTime совпал между stable и tree. Пропусков, лишних путей и metadata mismatches не обнаружено.
- Tree уменьшил raw CSV на 71.48% для R1 и на 69.37% для R3; ZIP стал меньше на 42.49% и 38.63% соответственно.
- На R1 локальный in-memory индекс ответил на точный путь в обоих форматах. Поиск по первым трём символам basename дал одинаковые 843 совпадения за 20.8/21.2 ms; поиск по расширению дал одинаковые 721 совпадение за 20.4/22.6 ms. Это замер harness по полученным индексам, не измерение UI-поиска в ChatGPT.
- На R3 те же три локальные проверки нашли 1 точный путь, 3,369 совпадений по basename и 52,934 по расширению в обоих форматах; метрики поиска по времени отдельно не снимались.

## Вывод и следующие действия

1. Tree формат сохраняет точные file metadata на двух корнях и в этих наборах уменьшает ZIP на 38.6–42.5%.
2. Для большого R2 текущая генерация tree упирается в 8 MiB closed-ZIP cap. Предложение 015 о независимом tree raw-part size (ориентир 16 MiB при сохранении stable-настроек) остаётся без реализации; после его реализации повторить tree только на R2.
3. Part 2 существует и открывается у пользователя; не заводить storage-loss fix на основании одного assistant-side `get_artifact` ответа `NOT_FOUND`. При необходимости отдельно сопоставить SHA-256 локального ZIP с manifest.
4. Настройка `FS_SNAPSHOT_TREE_MAX_RAW_PART_BYTES` ещё не реализована в runtime 014. Сначала реализовать task 015, оставить stable cap без изменений, собрать/развернуть комплект; после этого перезапустить независимый сервис и повторить только tree на R2.

В Git записаны только агрегаты. Production inventory, исходные artifacts и локальные байты в репозиторий не добавлялись.
