## R1 — P2: предложенная команда следующей страницы теряет limit

В `src/tools/list.ts:291` эффективный limit правильно включён в query identity.
Но вызов pageTrailer в `src/tools/list.ts:385` передаёт только nextCursor;
`src/core/fmt.ts` печатает команду `Next page: list {"cursor":"..."}`.
При нестандартном limit такой вызов использует default 20000 и не соответствует
исходному набору. Модель получает Invalid cursor, следуя инструкции сервера.
Это мешает пользоваться новым общим лимитом и провоцирует повторный scan.

Независимое воспроизведение через настоящий MCP Client/Server, synthetic root с
тремя файлами, единственный разрешённый root, остальные параметры по умолчанию:

1. Вызвать `list({"limit":2,"pageSize":1})`.
2. Первая страница содержит одну запись, totalEntries=2 и nextCursor.
3. Извлечь JSON из фактически возвращённой строки Next page и передать его
   следующему list без ручного дополнения параметров.
4. Получен `INVALID_INPUT: Invalid cursor. Request the first page without a cursor.`
5. Тот же cursor с явно повторённым `limit:2` успешно возвращает продолжение.

Контроль: `list({"pageSize":1})` с default limit и затем буквально предложенная
команда работают. В обоих случаях path отсутствует, flags/depth стандартные;
расхождение вызвано именно добавленным в identity limit. Прежняя общая проблема
cursor-only подсказки при нестандартном scope также требует учёта при исправлении.

Исправление: выдавать исполнимую команду продолжения с исходными параметрами
набора (path/depth/flags/limit; pageSize сохранять для удобства). Не ослаблять
проверку query identity: cursor с другим scope или limit должен отклоняться.
Если меняется общий formatter, проверить соседние find_files/search_text.

Нужна регрессия, которая разбирает и выполняет именно команду из text ответа,
включая нестандартные limit, path, depth и flags. Существующие проверки повторяют
аргументы вручную и потому не обнаруживают ошибочную подсказку. Проверить также
изменение pageSize, отсутствие нового обхода и предупреждение на последней странице.

## R2 — сопутствующая устаревшая подсказка TIMEOUT

Фактический ответ list при контролируемом истечении deadline:

```text
TIMEOUT: The operation was aborted due to timeout
Reduce scope, depth, or maxResults.
```

Источник: общий HINTS в `src/core/errors.ts:78`. Параметра maxResults у list нет;
новая документация корректно различает limit и pageSize, а runtime hint этому
противоречит. Это прежний дефект, не новая регрессия 010 и не отдельный блокер
приёмки. Рекомендуется исправить вместе с R1: нейтральный общий совет сужать
область/глубину или точный list-specific совет про limit. Не советовать снижать
pageSize для ограничения обхода; не увеличивать deadline вместо исправления.
Проверить фактический текст ошибки, а не только instructions/help.
