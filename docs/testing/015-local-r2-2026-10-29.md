# 015: локальная распаковка и scan/search R2 — 2026-10-29

## Входные данные и метод

Для одного и того же R2 использованы stable-артефакты из прогона 014 (11 ZIP) и tree-артефакты из job 015 (10 ZIP). Оба набора и извлечённые CSV находятся только в ignored `.tmp`; production inventory и ZIP не добавлялись в Git.

Локальный Windows harness на Python 3.12.3: SHA-256 каждого ZIP сверялся с его manifest, затем ZIP проверялся `zipfile.testzip()` и извлекался на диск. CSV разбирался `csv.reader`; поиск точного относительного пути, префикса basename и расширения выполнялся одним полным проходом по каждому набору. Для parity сравнивались точные относительные пути, размер и LastWriteTime; регистр символов сохранялся.

Tree занял на 65.7% меньше raw CSV и на 28.2% меньше ZIP bytes. Распаковка этого набора была на 52.8% быстрее. Все 21 ZIP прошли manifest SHA и CRC; распакованные байты совпали с manifest raw byte totals.

## Сканирование, поиск и соответствие

| Метрика | Stable | Tree |
| --- | ---: | ---: |
| file records | 2,843,566 | 2,843,566 |
| tree directory records | — | 345,216 |
| tree context/error records | — | 63 / 8 |
| Построение локального path→metadata индекса | 11.322 s | 24.483 s |
| Полный проход exact/prefix/extension query | 8.272 s | 20.277 s |

У обоих форматов совпали ответы на контрольные запросы: exact path — 1 hit; три символа префикса basename — 4,679 hits; extension — 5,738 hits. Все 2,843,566 точных relative paths совпали между форматами; `stableOnly=0`, `treeOnly=0`, расхождений size/LastWriteTime — 0.

Tree требует восстановить путь из depth и directory records, поэтому локальный Python parse/scan получился медленнее примерно в 2.16×/2.45×. Индекс при этом компактнее, а контрольное извлечение быстрее. Это измерение одного локального Python harness, не тест Excel, UI ChatGPT или внутренних search latency модели.

Пути сравнивались с сохранением регистра и нормализацией только разделителя. Case-insensitive folding сливает 6 case-distinct записей в каждом наборе; поэтому его не использовали для подсчёта точных путей. Имена и сами query values в протокол не записывались.

Оба server manifests помечают `complete=false`: 470 inaccessible skips; у tree дополнительно 8 error records. Сравнение подтверждает parity для выданных записей, а не полный обход всех исходных объектов.
