# 015: локальная распаковка и scan/search R2 — 2026-10-29

## Входные данные и метод

Для одного и того же R2 использованы stable-артефакты из прогона 014 (11 ZIP) и tree-артефакты из job 015 (10 ZIP). Оба набора и извлечённые CSV находятся только в ignored `.tmp`; production inventory и ZIP не добавлялись в Git.

Локальный Windows harness на Python 3.12.3: SHA-256 каждого ZIP сверялся с его manifest, затем ZIP проверялся `zipfile.testzip()` и извлекался на диск. CSV разбирался `csv.reader`; поиск точного относительного пути, префикса basename и расширения выполнялся одним полным проходом по каждому набору. Для parity сравнивались точные относительные пути, размер и LastWriteTime; регистр символов сохранялся.

## Сканирование, поиск и соответствие

| Метрика | Stable | Tree |
| --- | ---: | ---: |
| file records | 2,843,566 | 2,843,566 |
| tree directory records | — | 345,216 |
| tree context/error records | — | 63 / 8 |
| Один проход: exact path + basename prefix + extension | 6.924 s (медиана 3 проходов) | 5.248 s (медиана 3 проходов) |
| Построение полного path→metadata индекса | 8.272 s (медиана 2 проходов) | 6.025 s (медиана 2 проходов) |

В повторном замере ответы на контрольные запросы совпали: exact path — 1 hit;
префикс basename — 4,679 hits; extension — 5,738 hits. Полные индексы содержали
по 2,843,566 file records. Предыдущая независимая parity-проверка установила,
что все точные пути, размеры и LastWriteTime совпали между форматами.

Исправленный consumer harness разбирает один и тот же уже распакованный CSV.
Stable берёт путь, имя и extension из колонок. Tree хранит стек предков: точный
путь сравнивается по компонентам без полной сборки строки для каждого файла;
basename queries читают имя напрямую. В режиме полного индекса путь материализуется
один раз на файл из сохранённого полного пути родительского каталога. Прогоны
последовательные, на одном локальном Python 3.12.3; это небольшая локальная
выборка повторов без cold-cache контроля и оценки разброса.

Первоначальные timings 11.322/24.483 s для индекса и 8.272/20.277 s для scan
**заменены**: прежний tree таймер включал per-file list/join/normalization,
проверку duplicate set, cross-format lookup и metadata equality, а также
`Path(...).suffix`. У stable не было эквивалентного parity workload внутри
таймера. Эти значения измеряли дополнительную проверку tree, а не равную задачу
обработки.

На этом R2 dataset эффективный tree parser оказался примерно на 24% быстрее для
трёх query scan и на 27% для полного индекса. Это предварительное локальное
свидетельство для конкретного consumer algorithm, а не гарантия для любых данных
и не замер внутренней обработки ChatGPT; следующий опыт проверит ChatGPT отдельно.

Пути сравнивались с сохранением регистра и нормализацией только разделителя. Case-insensitive folding сливает 6 case-distinct записей в каждом наборе; поэтому его не использовали для подсчёта точных путей. Имена и сами query values в протокол не записывались.

Оба server manifests помечают `complete=false`: 470 inaccessible skips; у tree дополнительно 8 error records. Сравнение подтверждает parity для выданных записей, а не полный обход всех исходных объектов.
