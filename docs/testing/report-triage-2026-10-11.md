# Triage внешнего обзора от 11 октября 2026

Отчёт полезен как повод проверить поиск и память пагинации, но не подходит
как техническое описание текущего форка или готовый план изменений.
Проверка выявила два воспроизводимых дефекта поиска. Изменять ignore policy
или увеличивать лимиты хранения на основании этого отчёта не предлагается.

  `8df617ed0b23d6ce70db60a4f4e058c815e76d34ef34c35624c71ea5a0cddaae`.
  Исходный документ в Git не копируется.
- Сверены текущие контракты, код, проектная документация и опубликованные
  MCP schemas. Дополнительно выполнены вызовы настоящих handlers через
  in-memory MCP client/server на синтетических файлах, Node v24.15.0 / Windows.
- Это triage архитектурного отчёта, не полный security audit и не сравнение
  с актуальной внешней веткой upstream. Attribution отдельных дефектов

## Подтверждённые наблюдения поиска

Это результаты нашей дополнительной проверки, а не готовые findings из отчёта.

### P2 Фактический обход выходит за maxDepth

Оба инструмента используют `globEntries`: maxDepth применяется к уже полученному
совпадению в `processDirentMatch`, но не ограничивает descent `fs.glob`.
`guardedEntries` проверяет отмену только на переданных ему entries. Если glob
долго перечисляет записи, отфильтрованные глубиной, управление туда не попадает.

Синтетическая выборка: 3 текстовых файла непосредственно в root, 3 дочерние
папки, в каждой 10 вложенных папок с одним текстовым файлом. Всего 33 файла;
глубокие файлы имеют относительную глубину 2. Все содержат `triage-token`.

Для `find_files` вызов: pattern `**/*.txt`, maxDepth 0, maxResults 1,
includeIgnored true, explicit path. Для `search_text` те же параметры плюс
searchPattern `triage-token`. В поиске maxDepth 0 означает только base directory.

| Инструмент  | Raw glob matches | Из них глубже заданного scope | Собрано в ответном наборе | Возвращено на первой странице |
| ----------- | ---------------- | ----------------------------- | ------------------------- | ----------------------------- |
| find_files  | 33               | 30                            | 3                         | 1                             |
| search_text | 33               | 30                            | 3                         | 1                             |

Инструментация оборачивала настоящий `fs.promises.glob` и считала возвращаемые
Dirent до фильтрации глубины; содержимое глубоких файлов этим не читалось.
Отдельный диагностический прогон задерживал выдачу каждого глубокого совпадения
на 45 ms при FS_SEARCH_TIMEOUT_MS=1000. Инструменты завершились через 1453/1429 ms,
обработали ещё по 10 raw matches после deadline и вернули успех без timeout warning.
Это искусственная задержка для проверки кооперативной отмены, не benchmark диска.

Без переданного maxDepth оба инструмента сначала собрали 33 совпадения,
хотя maxResults был 1. Это соответствует текущему контракту: maxResults задаёт
страницу, а общий cap поиска равен 10000. Модель пока не может задать меньший
общий cap через этот параметр. Маленькая страница не ограничивает работу обхода.

Предложение: отдельная задача на ограничение реальной глубины и проверку отмены
во время фильтрации/ignore traversal. Отдельно определить общий limit и pageSize:
для find_files единица — найденный файл, для search_text — совпавшая строка;
лимит числа прочитанных файлов является другим контрактом. Не обещать жёсткое
прерывание уже зависшего OS I/O. Glob syntax, ignore/negation и PathGuard сохранить.

### P2 Команда Next page не воспроизводит поисковый запрос

Первая страница обоих инструментов предлагает `Next page: <tool> {"cursor":"…"}`.
Буквальное исполнение завершается validation error: отсутствует обязательный
`pattern` у find_files либо `searchPattern` у search_text. Повтор с исходными
аргументами и новым cursor успешно возвращает следующую страницу.

Причина: `pageTrailer` поддерживает nextArgs, но handlers поиска их не передают.
Кроме обязательных полей, надо сохранять path, flags, depth, context и остальные
параметры query identity; иначе следующая страница относится к другой области
или отклоняется. У list это уже исправлено в 010.

Предложение: включить исправление в задачу поиска и проверять исполнение JSON
из фактического текста ответа, включая explicit path при нескольких roots.

## Память и сроки пагинации

PageSnapshotStore ограничен количеством наборов (32), но не суммарными байтами.
TTL 60 секунд считается от создания и не продлевается чтением. Expired записи
удаляются при следующем create/read, либо clear; таймера освобождения памяти нет.
При бездействии истечение TTL само по себе память не освобождает.

ResourceStore отдельно ограничен 64 записями, 25 MiB суммарно и 10 MiB на запись;
его TTL также 60 секунд. Это не scratch/artifacts фоновых jobs: у последних
отдельные настройки и persisted lifecycle. Увеличение только TTL курсоров
не увеличит срок жизни resource URI.

Полезная небольшая исследовательская задача: измерить RSS/heap, размеры retained
sets, eviction/expired-cursor частоту при нескольких клиентах и search_text с
контекстом/длинными строками. По результату выбрать byte budget, период очистки
и необходимость операторских настроек. OOM или нехватка 32 записей этим triage
не воспроизведены. `server.json` — metadata публикации MCP, не runtime config.

## Рекомендация планированию

1. Следующее исправление инфраструктуры — поиск: реальный обход/отмена,
   исполняемая следующая страница и отдельно согласованный контракт лимитов.
2. Память и TTL страниц — измерения; повышение лимитов заранее не предлагать.
3. Ignore default оставить прежним. Для полного инвентарного обхода выбирать
   snapshot с явно заданной политикой, а не удалять фильтрацию у всех tools.
4. Сохранить отдельно уже известный terminal/cleanup follow-up job manager
   из review 010. Этот отчёт его не исследует и не закрывает.

Реализация и новая задача этим review не назначены. Следующий предметный опыт
005 остаётся proposed. Runtime, defaults и установленный сервис не менялись.
Полный npm run check повторно не запускался: проверены схемы, четыре depth
прогона и literal/correct continuation обоих инструментов на synthetic fixtures.
