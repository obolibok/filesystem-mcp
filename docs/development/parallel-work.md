# Несколько чатов, один репозиторий

## Разделение работы

Планирующий чат хранит задачу проекта, приоритеты и принятые решения. Coding-чат
получает одну карточку с результатом и критериями проверки. Review оценивает diff
относительно этих критериев. История переписки помогает обсуждению, а переносимый
контекст находится в Git.

Планирование владеет `docs/project/status.md` и общим brief. Исполнитель владеет
кодом в scope задачи и разделом «Work record» её карточки. Не редактировать общую
доску из нескольких worktrees: предложить изменение статуса в итоговом handoff.
Исправление очевидной опечатки не требует отдельного согласования; изменение
scope, публичного контракта или нового большого компонента требует обсуждения
с конкретным предложением и последствиями.

Варианты поведения и изменения контракта, уже разрешённые карточкой, исполнитель
выбирает самостоятельно и объясняет в Work record. Обсуждение нужно для выхода
за её границы, а не для повторного разрешения записанных в ней изменений.

## Перед началом

1. Проверить `git status`, текущую ветку, базовый commit и наличие карточки.
   Если карта проекта отсутствует, base устарел: сначала получить подготовительный
   commit, не восстанавливать требования из памяти.
2. Планирование назначает одному coding-чату ID/ветку и отмечает `active`.
   Участники не предполагают, что все остальные видят их uncommitted changes.
3. Создать отдельный worktree от последнего принятого checkpoint, без переноса
   чужих незавершённых изменений. Установить зависимости через `npm ci` внутри него.
4. Прочитать карточку, проверить её исходные предпосылки и воспроизвести дефект.
   Исторический baseline — ориентир, не замена текущей проверки.

Пример ручного запуска из чистого planning checkout с committed docs:

```powershell
git status --short
git log -1 --oneline
git worktree list
git worktree add -b codex/001-baseline-defects .worktrees/001-baseline-defects HEAD
Set-Location .worktrees/001-baseline-defects
npm ci
```

Команда создаёт новый worktree и ветку; повторно на тех же именах её не выполнять.
Если приложение уже создало изолированный worktree, использовать его и не создавать
ещё один. Не менять активную ветку planning checkout ради coding-задачи.
При старте через приложение убедиться, что выбранная база содержит committed docs:
неопубликованный локальный commit отсутствует в удалённом clone/cloud checkout.

`.worktrees/` игнорируется и предназначена для локальных изолированных checkout.
На другой машине нужно доставить commits обычным Git-путём, прежде чем начинать
задачу. Перед push учитывать, что локальный checkpoint ещё не опубликован.

## Во время реализации

- Работать в рамках одной карточки; новые находки записывать как follow-up.
- Не добавлять runtime-зависимости для процесса ведения задач.
- При пересечении файлов с другой активной задачей согласовать порядок интеграции.
  Разные worktrees предотвращают перезапись, но не устраняют логические конфликты.
- Не запускать глобальный форматтер на соседние части решения и не чинить все
  накопленные проблемы заодно. EOL-нормализация разрешена в задаче 001 явно.
- Проверять минимальные воспроизводящие сценарии, затем требуемый repository check.
  Ошибки окружения, skipped tests и функциональные failures описывать отдельно.
- Обновлять reference при изменении поведения. Исторический baseline не переписывать
  так, будто исправление уже существовало в исходной версии.

## Передача результата

В task card оставить: базу/ветку, сделанные изменения, выбранный контракт, команды
и результаты проверок, skips, известные ограничения и последующие задачи. Локальные
логи можно хранить в ignored scratch, но вывод должен быть понятен без этих файлов.
Checkout в tracked карточке обозначать логически или относительно репозитория;
абсолютный локальный путь при необходимости передавать только в handoff сообщении.

Сохранить изменения отдельным локальным commit/checkpoint для переноса в соседний
worktree. При handoff указывать фактический SHA из Git. Если commit пока отсутствует,
явно сообщить, что результат доступен только как working-tree diff.
Не включать commit's own SHA в его текст: записать его в финальном сообщении/доске
при интеграции. Commit не означает разрешение на push, merge upstream или release.

Шаблон сообщения планированию:

```text
Задача: <ID>, ready for review.
Ветка / base / итоговый commit: <фактические значения>.
Результат: <поведение после изменения>.
Проверки: <команды, pass/fail/skips; где проверяли>.
Acceptance: <что выполнено; что не выполнено и почему>.
Риски / следующие задачи: <только значимое>.
```

Планирование или назначенный reviewer читает diff, сопоставляет результат с
acceptance и проверяет влияние на зависимые задачи. Только после принятия и
интеграции центральный статус становится `done`. Merge-конфликты и неисполненные
критерии остаются видимыми; зелёный отдельный тест не заменяет остальную приёмку.

## Что хранить в Git

Хранить task cards, brief, ADR, обезличенный baseline, код и synthetic fixtures.
Не полагаться на ignored `reports/`, `.tmp/`, содержимое `node_modules/`, PDF чата
из Downloads или абсолютные пути другой машины. Производственные inventories и
ZIP могут раскрывать устройство предприятия даже без содержимого файлов.
