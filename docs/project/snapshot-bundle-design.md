## Наблюдение и изменение границ

Пользователь сообщил о предыдущем CSV-снимке файлового индекса около 500 МБ.
Генерация занимала примерно 20–30 минут; файл приходилось делить на части до 50 МБ
и складывать их в ZIP. Это пользовательский опыт, не измерение текущего коннектора.
Предоставленный архив разобран: 2 899 231 запись, 448 508 534 bytes CSV в десяти
частях, 35 161 531 bytes ZIP. [Измерения и границы проверки](../testing/snapshot-shape-2026-09-20.md).
Отдельные ZIP для существующих частей занимают 1 465 809–5 527 543 bytes;
это основание для следующего synthetic live опыта, а не уже проверенная доставка.
Время исходного обхода по архиву не восстанавливается. В Git только обезличенные выводы.
50 МБ не считаем доказанным пределом нашего маршрута ChatGPT/MCP.

Предлагается проектировать 003 и 004 вместе. Уже 003 должна выдавать пригодный
к получению сжатый snapshot, включая управление долгой операцией, разбиение,
хранение и доставку. 004 повторно использует этот механизм для выбранных originals.
Реализацию выполнять последовательно, чтобы два coding-чата не меняли один core.

## Предлагаемый сценарий

1. Короткий вызов запуска проверяет корни, параметры и квоты, регистрирует задание
   и возвращает job ID. Повтор запуска с тем же request key и параметрами возвращает
   то же задание; потерянный ответ не должен запускать второй дорогой обход.
2. Фоновое задание обходит разрешённые источники и потоково сериализует metadata.
   Память и число открытых файлов ограничены; полный список не собирается в RAM.
   Монолитный несжатый файл на 500 МБ не является обязательным промежуточным этапом.
3. Записи объединяются в части с единым форматом и схемой, каждая часть сжимается.
   Границы проходят между целыми записями с корректным UTF-8 и quoting. Входной
   опыт — CSV; проверить его схему и multiline/escaping перед фиксацией формата
   snapshot. Если выберем CSV, каждая часть содержит свой header; простое деление
   по переводам строк не гарантирует границы CSV-записей.
4. Отдельный короткий вызов статуса возвращает фазу, счётчики, elapsed time,
   причины пропусков и сведения о результате. Процент не придумывать без известного
   общего количества. Клиент опрашивает статус с интервалом, не держит один долгий вызов.
5. После завершения доступны summary/manifest и отдельные части по artifact ID.
   Каждая выдача содержит одну ограниченную часть; повтор выдачи не повторяет обход.
   Получатель проверяет SHA-256, распаковку и число записей по manifest.
6. Явная отмена останавливает задание и убирает незавершённые результаты. Обрыв
   HTTP-запроса после регистрации задания сам по себе задание не отменяет.

Имена и точные схемы tools пока не выбраны. Проект не предполагает, что клиент
поддерживает native MCP Tasks, progress notifications или серверные callbacks:
базовый сценарий должен работать через обычные tools запуска/статуса/получения/отмены.

## Размеры и упаковка

Нужны отдельные конфигурируемые ограничения:

- Несжатые bytes одной части индекса: размер, с которым работает анализатор.
- Bytes готового архива: размер одной передачи и единица повторного скачивания.
- Размер MCP-ответа: base64 blob занимает `4 * ceil(archiveBytes / 3)` символов,
  дополнительно нужны JSON и metadata. Текущий get_file читает весь файл в память.
- Суммарный объём задания, число частей, дисковая квота и число активных заданий.

Предпочтение первой версии — самостоятельные обычные ZIP-файлы с ограниченными
частями индекса внутри. Один общий ZIP допустим только если он сам укладывается
в предел доставки. Нарезка CSV по 50 МБ внутри единственного огромного ZIP не
ограничивает размер передачи. Не использовать зависимые многотомные ZIP как основу.
Коэффициент сжатия заранее не гарантируется: проверять окончательный размер архива
с ZIP overhead; превышение требует переразбиения либо понятной ошибки, а не выдачи
слишком большого файла. Обязателен тест плохо сжимаемых metadata.

Старые части имеют около 45 MiB до сжатия; это измерение, не подтверждённый лимит. Рабочие значения
выбрать после size ladder в целевом ChatGPT: для каждого опыта записать raw/ZIP/wire
bytes, время передачи, получение файла, независимый hash и успешное чтение записей.
Порог из [OpenAI File inputs](https://developers.openai.com/api/docs/guides/file-inputs)
относится к файлам-входам API; переносить его на embedded resources нашего MCP нельзя.

## Общая основа и ограничения первой версии

- Владелец заданий живёт на уровне процесса/HTTP endpoint. `createServer` в HTTP
  вызывается для каждого запроса; сохранить job только в ToolCtx/per-request server
  недостаточно. У job собственная отмена, отделённая от request signal после submit.
- Готовые результаты и их metadata находятся в отдельном служебном каталоге
  с квотой и сроком хранения. Удаление не затрагивает выдаваемый в этот момент файл;
  активные записи защищены от cleanup. TTL результата отсчитывается от готовности.
- Не расширять source roots ради выдачи scratch. Доступ к артефакту проверяется
  сервером в текущем контексте доступа; знание artifact ID само по себе не даёт прав.
  Source I/O остаётся за PathGuard/GuardedFileSystem. Источники не изменяются.
- ResourceStore/PageSnapshotStore с TTL 60 секунд не используются как job/artifact
  storage. Нужен отдельный lifecycle, включая full disk, ошибку сжатия и cleanup.
- Снятие cap с list/find_files не делает обход потоковым. Существующий list
  накапливает/сортирует массив, а globEntries заранее собирает пути .gitignore.
  Память на очередь обхода, правила ignore и compression buffers тоже ограничена.
- Для первой версии предлагается сохранять metadata и готовые результаты на диск.
  После перезапуска незавершённые задания получают явный interrupted, готовые
  доступны до истечения TTL. Автоматическое продолжение обхода с checkpoint
  в первоначальный scope не включать; это отдельная сложность согласованности.
- Повторное получение части не должно менять её bytes. Незавершённый/усечённый
  результат никогда не объявляется полным. Snapshot описывает интервал наблюдения,
  а не атомарное состояние изменяющегося дерева.
- Задание создаёт служебное состояние: поведение --read-only для источников и MCP
  annotations для submit/cancel описать отдельно и честно. Нельзя автоматически
  переносить readOnlyHint/idempotentHint с get_file на все новые операции.

## Этапы и приёмка

003 включает общую основу заданий/артефактов и snapshot как первый её сценарий.
Внутренние этапы: контракт и проверка размеров доставки; минимальная основа;
потоковый обход со сжатием; полный сквозной прогон. Это этапы одной связанной работы,
а не разрешение на параллельную правку core разными исполнителями.

В 004 остаются выбор набора originals, сохранение имён и происхождения,
byte-exact упаковка, hash файлов и фиксация их изменений/недоступности при сборке.
003 уже содержит сжатие индекса; 004 не откладывает эту возможность на будущее.

Для 003 дополнить прежнюю проверку дерева >20 000 entries:

- Отдельный нагрузочный профиль с около 500 МБ сериализованных metadata;
  synthetic pipeline load и реальный обход дерева измеряются отдельно.
- Ограниченная память при генерации и выдаче, время/peak memory/disk/raw/ZIP/wire
  bytes записаны. Большой прогон не обязан входить в каждый быстрый CI запуск.
- Задание длится дольше тестового client timeout, переживает потерю соединения;
  следующий HTTP-запрос видит его состояние. Повтор submit не создаёт дубликат.
- Части отдельно распаковываются, hashes/число записей совпадают, все границы и
  квоты соблюдены. Полный набор на неизменяемом дереве не имеет потерь и дублей.
- Ошибки доступа, исчезающие файлы, junction за пределы root, отмена, full disk,
  истечение TTL и перезапуск дают воспроизводимый и честно описанный результат.
- В ChatGPT реально получены manifest и несколько частей, выполнены распаковка,
  проверка hashes и обработка записей. Локального SDK PASS недостаточно.
