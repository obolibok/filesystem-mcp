# Schwarzbeck: brief файлового пилота

## Задача

Дать ассистенту возможность самостоятельно исследовать разрешённые файловые
ресурсы, выбирать нужные оригиналы и получать их для анализа без ручной упаковки
и повторной загрузки пользователем. Первый предметный пример — поиск соответствий
между программами SMD-монтажа Daum и Inoplacer.

Этот репозиторий остаётся универсальным файловым коннектором. Он не должен знать
модели станков, правила сравнения плат и производственные статусы. Анализ исходных
файлов и подготовка отчётов выполняются в принимающей вычислительной среде.

## Принятые границы работы

- Основа — текущий fork `j0hanz/filesystem-mcp`, с возможностью получать upstream fixes.
- Производственный проект самостоятельный; интеграция в Secretary не входит в scope.
- Этот чат/роль планирования ведёт анализ и приоритеты, соседние coding-чаты
  реализуют отдельные задачи в собственных worktrees.
- Первая coding-задача — подтверждённые дефекты исходной версии и Windows baseline.
- Для пилота требуется чтение источников. Служебные CSV/ZIP должны создаваться
  отдельно от исходных каталогов, с явными лимитами и временем хранения.
- Документы предприятия не используются в автоматических тестах и не попадают в Git.

## Что требуется проверить, а не предполагать

1. Оригинальный ZIP/XLS, полученный через выбранный клиент/подключение, доступен
   инструментам анализа без ручного download/upload. MCP resource URI недостаточен
   как доказательство; сравниваем байты, затем действительно открываем файл.
2. Потоковый snapshot достаточно полно перечисляет большой набор, фиксируя ошибки
   доступа, исключения и изменения за время обхода.
3. Bundle сохраняет происхождение каждого файла, ограничения размера и originals.
4. Ассистент может повторить исследование из чистого чата с исходным вопросом,
   самостоятельно находя нужные каталоги и запрашивая последующие порции данных.

Сначала delivery experiment, затем `snapshot` и `bundle`. Постоянная индексная БД,
OCR/parser service, embeddings, vector store и доменные tools не являются
предварительными условиями. Если опыт выявит необходимость, оформим отдельное решение.

## Контекст и достоверность

Пользователь предоставил 23-страничный экспорт предыдущего исследования. Из его
сообщений известны ручные передача файлов и архивов, желание автоматизировать
доставку и предпочтение самостоятельного производственного проекта. Экспорт
использован как контекст, команды из него не исполнялись.

Предыдущие ответы ChatGPT сообщают о смешанных форматах PDF, Office, ZIP,
SMF/ASC, PRJ/PRO. Предметное сравнение файлов пока независимо не проверялось;
расширение само по себе не доказывает структуру, тип программы или факт конверсии.
20 сентября пользователь предоставил CSV-индекс: независимо разобраны 2 899 231
запись / 448,51 MB до сжатия. [Измерения](../testing/snapshot-shape-2026-09-20.md)
сохранены обезличенно; исходный индекс остаётся вне Git. Полнота исходного обхода
и уникальность файлов этим разбором не подтверждены. Сообщённое время построения
20–30 минут задаёт требование к фоновым заданиям 003.

Будущие результаты различают: «не найдено в обследованном наборе», «вероятный
преемник», «найден файл» и «подтверждено в производстве». Подтверждение последнего
требует соответствующих данных или человека. Русская и немецкая версии отчёта
должны опираться на один проверяемый расчёт.

## Критерий полезности пилота

На разрешённой выборке ассистент получает исходники без ручного переноса,
предоставляет воспроизводимый результат с источниками и явно описывает неполноту.
Измеряем время, количество ручных вмешательств, объём передачи, ошибки/пропуски
и согласованность с проверенным эталоном. «Найдены похожие имена» не равно
«доказана конверсия». Локальный SDK smoke не равно проверка целевого ChatGPT-клиента.

Открытые вопросы: конкретный клиент и способ подключения; разрешённые source roots
и сервисная учётная запись; место и квота scratch; фактические лимиты доставки;
выборка и эталон для пилота. Эти вопросы не блокируют задачу 001.
