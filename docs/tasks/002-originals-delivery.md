# 002: Проверить доставку originals в среду анализа

Статус и назначение: [центральная доска](../project/status.md).
Зависимости: 001, принята и интегрирована через PR #1.

## Зачем

До реализации `snapshot` и `bundle` проверить ключевую предпосылку пилота:
ассистент получает оригинальные ZIP/XLS через файловый коннектор и действительно
открывает их в принимающей среде анализа без ручного download/upload пользователем.
Результат задачи — воспроизводимый эксперимент и решение о следующем шаге;
работоспособность конкретного клиентского пути пока не доказана.

## Контекст и источники

- [Brief](../project/brief.md): задача пользователя и границы универсального коннектора.
- [Architecture](../reference/architecture.md): существующие resources, guard и лимиты.
- [Workflow](../development/parallel-work.md) и [Windows](../development/windows.md).
- [Задача 001](001-baseline-defects.md): исходные bytes в file resources сохранены;
  принятие и итог CI записаны на центральной доске.
- Принятый checkpoint до постановки 002: `ad12602da0186de8e6c7d8c771b908f553104457`.
  Рабочая база должна также содержать эту карточку; фактический SHA записать при старте.

Текущий binary file resource возвращает base64 blob по URI
`filesystem-mcp://file/{+path}`. Это не свидетельство появления файла в ChatGPT.
`read(includeHash)` хеширует возвращённый текст и не заменяет SHA-256 оригинала.
Полное чтение/raw resource по умолчанию ограничено 10 MiB; cached tool results
имеют отдельные ограничения и TTL. Перепроверить нужный контракт в текущем коде.

Целевой сценарий — анализ в ChatGPT. Конкретный режим клиента, способ подключения
и доступная вычислительная среда ещё не выбраны. Установить их в начале работы;
если это нельзя выяснить из доступного контекста, запросить недостающие сведения
у пользователя одним коротким вопросом, параллельно готовя локальный стенд.
Локальные SDK/Codex-проверки — отдельный этап, не замена целевому эксперименту.
Актуальные ограничения клиента проверять по официальной документации с URL и датой,
отделяя документированную возможность от фактически проверенной.

## Scope и владение

Исполнитель владеет этой карточкой, протоколом и результатами в
`docs/testing/originals-delivery.md`, небольшими воспроизводимыми scripts/fixtures
для опыта и содержательными проверками добавленного кода. Предпочесть существующий
MCP-контракт; необходимости менять runtime заранее нет.

Разрешены локальный стенд с synthetic-only root, генерация fixtures в ignored
scratch, минимальный экспериментальный адаптер доставки и небольшие исправления
существующего пути, если они подтверждены воспроизведением. Guard, read-only,
размерные ограничения и отмена запросов сохраняются. При изменении поведения
обновить reference и добавить соответствующие regression tests.

Если необходимы новый публичный контракт, внешний сервис или постоянное хранилище,
подготовить конкретное предложение с причиной, альтернативами и стоимостью;
это отдельное решение планирования. Не начинать `snapshot`, production `bundle`,
OAuth/multi-user, OCR, Office/domain parsers на сервере, индексы или vector store.
Библиотека для создания/проверки synthetic XLS на стенде не является серверным parser.
Не добавлять runtime-зависимости только ради эксперимента.

Использовать уже созданный приложением worktree и ветку `codex/002-originals-delivery`,
если она свободна; не создавать вложенный worktree. Общую доску, brief и правила
совместной работы ведёт планирование. Не включать производственные документы,
inventories, архивы, секреты или персональные абсолютные пути в Git. Не публиковать
source roots ради опыта; для подключения извне использовать только согласованный
способ и изолированный synthetic root.

## Протокол эксперимента

1. Зафиксировать base/branch, версии среды, целевой клиент и его режим, transport,
   способ авторизации без секретов, настройки лимитов и точный маршрут передачи.
   Различать разовую настройку подключения и ручные действия при передаче файла.
2. Воспроизводимо подготовить небольшой ZIP с UTF-8/Unicode-именами и binary entry,
   а также настоящий legacy `.xls` с известными контрольными ячейками. `.xlsx`
   можно добавить отдельно; переименование CSV/XLSX в `.xls` не подходит.
   Проверить валидность fixtures независимым reader, сохранить размеры и SHA-256.
   Генератор/инструкции переносимы, generated artifacts остаются вне Git.
3. Проверить byte-exact получение обоих originals локальным MCP-клиентом через
   существующие resources. Это контроль исправности серверного участка цепочки.
4. Из целевого клиента найти и запросить те же файлы через коннектор. Зафиксировать
   вызовы и результаты, а при отказе — точную границу и наблюдаемую ошибку.
   В принимающей среде программно вычислить SHA-256 реально доставленных bytes,
   открыть ZIP, проверить имена/содержимое entries и прочитать контрольные ячейки XLS.
   Ожидаемый hash или содержимое, повторённые моделью, доказательством не являются.
5. Повторить успешный путь для обоих форматов, затем проверить поведение ниже
   и выше применимого лимита с небольшим тестовым бюджетом, если это позволяет
   стенд. Не устраивать нагрузочный тест. Для временных ссылок/ресурсов проверить
   истечение срока и понятную ошибку; если путь не использует TTL, отметить N/A.
   Проверить отказ доступа вне synthetic root. Неисполнимые проверки обозначить явно.
6. Сохранить компактную матрицу результатов, команды воспроизведения, измерения
   размеров/времени, ручные действия и конкретный вывод для задач 003/004.

Запрещённые подмены доказательства: один resource URI, blob только в локальном SDK,
ссылка без успешного чтения полученного файла, вставка base64 пользователем,
ручной upload, повторная генерация исходного fixture в analysis runtime или чтение
общего локального диска в обход коннектора.
